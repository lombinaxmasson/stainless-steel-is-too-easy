# 流化床工业供热

流化床燃烧室是由独立高塔与旋风分离器组成的 HU 热源。它燃烧固体煤系燃料，用 KU 驱动鼓风，从后部接口输出 GregTech HU。外接 **HU 烟道**（`heat_duct`）与 **共享加热板**（`heating_plate`）独立放置，也可接其他原生 HU 热源。流化床整机最大输出为 **2304 HU/t**，外接九块板不会将热量复制九份。

外观沿用本项目原创的 HBM 风格低多边形 OBJ 与像素贴图。成型后显示完整工业设备；未成型或拆掉必需零件时显示普通方块。结构预览与建筑之杖使用同一份旋转布局，合成材料可在游戏配方查看器中查询。

## 搭建

以**控制器朝北、控制器自身为 `(0,0,0)`**描述相对坐标。X 正方向向控制器右侧，Y 向上，Z 正方向向后。其余三个朝向将整套结构一起旋转。

本体结构共 **71 个方块**：控制器 1、结构外壳 35、基础 33、结构烟道 2；另外保留炉内 6 格空气。主体方块范围为 `X=-3…3、Y=0…7、Z=0…4`，即 **7×8×5**。外接运输烟道、加热板和受热设备不参与本体成型。

| 部件 | 相对坐标 | 数量 |
| --- | --- | ---: |
| 流化床控制器 | `(0,0,0)` | 1 |
| 主装置基础 | `X=-3…3、Y=0、Z=0…4`；扣除控制器与后部出口 `(0,0,4)` | 33 |
| 炉体四根结构柱 | 每层 `(-1,Y,1)`、`(-1,Y,3)`、`(-2,Y,2)`、`(0,Y,2)`，`Y=1…6` | 24 |
| 炉顶结构 | `X=-1…0、Y=7、Z=2…3` | 4 |
| 分离器支柱 | `(2,Y,3)`，`Y=1…6` | 6 |
| 分离器横向支撑 | `(2,4,2)` | 1 |
| 上部连接烟道 | `(1,6,3)` | 1 |
| 后部出口结构烟道 | `(0,0,4)` | 1 |
| 必须为空的炉内空间 | `(-1,Y,2)`，`Y=1…6` | 6 格空气 |

后部出口向后连接第一节外置 HU 烟道，位置为 **`(0,0,5)`**。用于本体的保温烟道（`fluidized_bed_duct`）仍是结构零件，外接运输要使用新 HU 烟道（`heat_duct`）。拆掉外管或加热板不会使高塔失去成型；路径无效时，高塔停止向该路径交付热量。控制器正面、上方和下方预留给外部设备；操作和库存均位于控制器，外观中的料斗与风机没有额外库存。

成型后的主装置基础采用 0.28 方块高的底架碰撞与选中轮廓，匹配钢架外观；控制器及独立加热板仍保留完整方块接触面。拆坏本体后基础恢复普通完整方块，修复成型后重新使用低底架轮廓。

### 从旧固定炉台结构迁移

旧控制器的库存、档位、开关、剩余燃料热量与 HU/KU 缓存沿用原有保存字段。更新不会自动替换世界中的旧零件或铺设新管道。以下仍使用控制器朝北的相对坐标，其余朝向随控制器旋转：

| 旧位置 | 更新后的处理 |
| --- | --- |
| 塔底后排 `(1,0,4)`、`(2,0,4)`、`(3,0,4)` 的旧结构烟道 | **三格都换成流化床基础 `fluidized_bed_foundation`**，否则新本体不能成型 |
| `(0,0,4)` 与 `(1,6,3)` 的旧结构烟道 | 保留，分别作为后部出口和上部连接烟道 |
| 塔外 `(4,0,2)`、`(4,0,3)`、`(4,0,4)` 的旧结构烟道 | 已不属于本体；不会运输新网络的 HU，可拆下回收 |
| `X=5…7、Y=0、Z=1…3` 的九块旧炉台基础 | 已不属于本体，可保留为普通支撑 |
| `X=5…7、Y=1、Z=1…3` 的九块旧供热板 | 拆下后用无序转换配方 **1:1** 制成 `heating_plate`，再放回原位 |

最后从 `(0,0,5)` 铺设实际 `heat_duct` 接到新板组；下一节给出八节管的示例。原位置的大型 AOD 或大型坩埚可以保留，只需更新下方热板并接通外管。旧炉台和塔外烟道不再是成型条件，也不再由高塔直接向其上方坐标发热。

## HU 烟道与共享加热台

HU 烟道只运输热能，不承载流体，也不需要模拟烟气物品。管与管可从六面相连；加热板从四个水平面接入管或相邻板，只向上方接触的设备输出。竖直叠放的加热板属于不同平台，不能经由板的顶面或底面串联传热。

一个有效网络最多包含 **12 节烟道**，并连接**一组同层、水平连通、位于 3×3 范围内的 1～9 块加热板**。单板即可工作；九块板共享已有 HU，每块顶部上限 **4096 HU/t**，九板合计最高 **36,864 HU/t**。管网全部入口共用 **73,728 HU/t 的总扣款预算**，包含接收设备实际得到的热量与途中损耗；增加入口数量不会增加这个预算。目前单组九板上限通常先成为限制。

板组内部共享无损。热量从某根管的缓存发出时，按它到板组的实际路径计算损耗，包含这根管自身；每经过一节管线性损失 **1%**。例如三节管从缓存扣除 1000 HU，可交付 970 HU，记录损失 30 HU。只扣除对方实际接受的热量及其对应损耗，向多个板分配同一入口时累计取整，避免把同一小数损耗重复计为九次。某板上方没有接收设备时，它未接受的份额留在原缓存中。

烟道缓存为每块 **2,949,120 HU**，板缓存为每块 **163,840 HU**。它们不会生成热量；可通过原生 HU 注入接口接其他热源。封闭管环、超过 12 管、板组超出 3×3 或 9 块、经管道连接多个分离板组，以及碰到未加载区块边界时，整个相应网络拒绝新输入并停止输出，不强行加载区块。断管后，上游不会隔空供热，下游已存于有效板组中的余热仍可继续输出。右键可查看缓存与运输状态，Jade 还显示管板数量、实际输出和损耗。

以下八节管示例保留了侧置 3×3 炉台位置：

```text
(0,0,5) → (1,0,5) → (2,0,5) → (3,0,5) → (4,0,5)
                                                    ↓ 向上
                                               (4,1,5)
                                                    ↓ 向前
                                               (4,1,4)
                                                    ↓ 向前
                                               (4,1,3) → 加热板组 X=5…7、Y=1、Z=1…3
```

该路线从首管输入到板组的运输损耗为 8%；受热设备底部放在 `X=5…7、Y=2、Z=1…3`。可在板下放普通支撑块，它们不参与网络校验。不要沿板组边缘额外铺回路；两条管路径绕回同一板组也视为环路。旧 `fluidized_bed_heat_plate` 是保留的旧零件，可用转换配方制成新 `heating_plate`。

## 功率、燃料与操作

右键控制器打开界面，将煤系燃料放入输入槽，再打开燃烧开关。新控制器默认关闭，默认功率为第 2 档。用**螺丝刀右键控制器**循环切换 1→2→3→4→1 档，档位与开关会保存。

| 档位 | 热源最大输出 / 新燃烧速率 | 燃烧所需 KU/t |
| --- | ---: | ---: |
| 1 | 576 HU/t | 8 |
| 2（默认） | 1152 HU/t | 16 |
| 3 | 1728 HU/t | 24 |
| 4 | 2304 HU/t | 32 |

可以使用原版煤、木炭、煤块，以及材料量为整 U 的煤、焦炭、褐煤等煤系粉、宝石和材料块。小撮粉、小堆粉与其他不足 1 U 的碎料不接收，避免碎料拆分使灰量倍增；单个物品最多接受 64 U，木板、木制机器和其他普通可燃物也不作为流化床燃料。

燃料收益采用**原版流化床配方热值的 150%**。原版流化床配方已含普通燃料热值的 3 倍，因此每 U 的入库热值为 `原版材料燃烧 ticks × 25 × 3 × 150%`。按原版材料表取值，不依赖普通熔炉物品燃烧时间；这些值表示产生的热量，实际输送仍需扣除蓄热散失。

| 燃料 | 原版流化床热值 / U | 本机热值 / U |
| --- | ---: | ---: |
| 煤、木炭、褐煤焦炭 | 120,000 HU | 180,000 HU |
| 焦煤 / 焦炭 | 240,000 HU | 360,000 HU |
| 褐煤 | 60,000 HU | 90,000 HU |
| 无烟煤 | 360,000 HU | 540,000 HU |
| 石油焦 | 480,000 HU | 720,000 HU |

原版煤和木炭按 1 U、煤块按 9 U 计量；GT 燃料按物品的材料组成计量。因此一块煤块提供 **1,620,000 HU**，9 U 石油焦粉块提供 **6,480,000 HU**；压块与拆分不会改变单位材料收益。既有存档中已投入燃料的剩余热量保留原值，150% 收益用于更新后新投入的燃料。

对照基准为 GT6 `Loader_Fuels` 与当前 CE `OriginalFluidBedFuelRows` 的材料热值。原版每 U 粉还需 72 mB 熔融方解石，设备效率最高为 100%；当前本机仍采用 KU 鼓风和独立排灰规则，尚未接入方解石消耗，因此上述 150% 是燃料产热倍率，不是整条生产线成本的比较。更高输出档位和对应热容量仍属于后续平衡方案，当前实现以本页功率表为准。

原版及 GT 木炭产生小撮灰烬（`Ashes`），其余煤系燃料产生小撮暗灰（`DarkAshes`）；材料块按材料单位数预留相应灰量。

每次投入一份燃料时，必须先在输出槽中完整放下对应的灰，才会扣除燃料。灰槽堵塞会停止新投料，已经投入并预留了灰的燃料仍可继续燃烧。HU 缓存为 **576,000 HU**，KU 缓存为 **6,400 KU**；缺少 KU、结构破坏或关闭燃烧时，剩余燃料热值保留。

冷炉有预热过程：每 tick 最多释放当前热缓存的 **1/40**，同时受当前功率档位限制，经后部接口交给真实相邻烟道，再由外部网络分配给板组。新燃烧产生的热量从下一 tick 起可供输出，因此不能把档位额定值当作冷启动第一 tick 的实际热量。停燃后也按缓存逐渐衰减输出；接收设备得到的热量还要扣除外管损耗。

**红石高信号停止燃烧，低信号允许恢复。**它与界面开关都控制新产生的热量，缓存中的余热仍会传给有效外管并自然散失。已加热的大 AOD 或坩埚也保留自身炉温，因此关闭开关不会让受热设备立即冷却。本体结构不完整时停止源头输出；外管和板中已交付的余热仍属于外部网络。修复后可继续利用热源剩余缓存。

安装 Jade 时，查看控制器或其绑定零件可看到结构状态、当前档位、实际 HU/t、热缓存、KU 缓存、剩余燃料热值，以及停机原因。额定输出、实际输出和剩余热量分别显示，方便判断缺风、缺燃料、灰槽堵塞或受热设备没有接好。

## 自动化接口

| 功能 | 控制器的可用面 | 接法 |
| --- | --- | --- |
| 固体燃料输入 | 顶部、正面 | 输入槽 0；推荐正前方漏斗朝向控制器 |
| 灰输出 | 底部 | 输出槽 1；推荐控制器正下方安装漏斗 |
| KU 鼓风动力 | 顶部、正面 | 推荐控制器正上方安装朝下输出的 KU 动力源；KU 不会转化为 HU |
| 红石停机 | 控制器邻接信号 | 有信号暂停新燃烧 |
| 热源 HU 输出 | 本体后部出口 `(0,0,4)` 的后面 | 接第一节外管 `(0,0,5)` |
| 加热台 HU 输出 | 各加热板顶部 | 直接接触受热设备的下表面 |

结构基础会占据左右侧面的相邻方块，推荐同时采用**正面进料、底部排灰、顶部接 KU**，三者不争用位置。接口装好后，可以从两侧 0.28 方块高的矮底架上方选中控制器，打开界面或使用螺丝刀调档。输入口拒绝非煤系物品，也不能向灰槽反向塞入燃料；输出口只能取出灰，不会取走尚未燃烧的燃料。整机不设气体或液体罐，鼓风使用 KU 动力接口。外部 HU 注入控制器会被拒绝。

板组可以按有效管路放在其他位置，输出目标始终是实际加热板的正上方。外管需要连续的实体方块和已加载路径；热源不再直接向固定的九个远程坐标发送 HU。

## 接大型 AOD 与原版大型坩埚

以下坐标采用上面的八节管与侧置九板示例；将板组移到其他位置时，受热设备也需相应平移。

**大型 AOD：**将 AOD 控制器放在流化床相对坐标 **`(6,3,0)`**，朝向与流化床控制器一致，再按[大型 AOD 使用说明](large-aod.md)搭建。AOD 的九格炉底会正好落在 `(X=5…7,Y=2,Z=1…3)`，与供热台九格接触，不需要再放九台独立燃烧室。AOD 的氧气、氩气、投料炉盖和浇铸口仍按自身规则使用。

**GT6CE 原版大型坩埚：**将坩埚底部中央控制器放在 **`(6,2,2)`**，以该位置为中心搭建对应材料的 3×3×3 开口坩埚。底部控制器和周围八格炉壁共同覆盖供热台；炉壁必须与坩埚材料变体匹配，内部两格保持空气。两种炉子都通过原有 HU 接收接口升温，流化床不修改其炉温上限、熔炼或精炼规则。

## 资源与验证入口

150% 燃料收益此前通过 `:neoforge:fluidizedBedTest` 的 14 项 JVM 回归：四档分别从冷炉烧完 4 份煤、持续接收并排尽余热，热源交付为 718,476～718,529 HU，对照原版 480,000 HU 为 **149.683%～149.694%**；其余 1,471～1,524 HU 全部记为热源散热。这是热源出口账本的历史基准，**不包含本次新增外管损耗**，也不代表任意实际负载下的最终收益。

`python scripts/models/install_fluidized_bed.py` 生成并安装运行时 OBJ、像素 atlas 与模型资源。结构和热源逻辑位于 `FluidizedBedStructure`、`FluidizedBedCore`；独立运输逻辑位于 `HeatTransportCore` 与两平台的 `HeatTransportBehavior`。合成配方和语言文件独立维护。查看模型可打开 `art/fluidized_bed/preview.html`。

实际游戏测试复用隔离目录 `neoforge/build/large-aod-smoke`，控制器沿 `X=768…992、Y=100、Z=0` 每隔 32 格布置；每组只整理控制器周围水平各 12 格、下 2 格至上 10 格的测试区域，不接触既有 AOD 测试区域或玩家存档。测试代码只在 `-PssiteSmokeTest` 下加载，不进入发布 JAR。

```powershell
scripts/build.ps1 :neoforge:compileSmokeTestJava
scripts/build.ps1 :neoforge:runServer -PssiteServerDir=build/large-aod-smoke -PssiteSmokeTest
python scripts/testing/fluidized_bed_server.py
python scripts/testing/heat_transport_server.py
```

服务器需已由使用者配置并接受其 EULA，启用该隔离目录的本机 RCON。脚本不创建存档、不接受 EULA、不接收远程服务器地址，并在有在线玩家时拒绝修改世界。流化床夹具检查合成配方实际加载、四向本体成型与拆修、热源到首管的实际 HU 总账、外管断开后本体仍成型且停止供热、缺风/满灰/红石/螺丝刀控制、真实漏斗进煤排灰、真实大型 AOD 与原版大型坩埚升温，以及运行时 NBT 读写。自动化阶段推进 160 tick 后经原生 KU 接口补风，再推进 100 tick，保留四份煤对应四份灰的断言。测试后服务器保持 tick 冻结，便于继续检查。

`HeatTransportTests` 提供 20 项纯 JVM 检查，执行入口为 `scripts/build.ps1 :neoforge:heatTransportTest`。它覆盖一到十二节的线性损耗、九板共享、部分拒收、多个入口共用预算、同 tick 重入与拓扑重配、超长/超大/环路/多层板拒收、未加载边界、断路余热，以及接收方回调中拆管或卸载后立即停止后续传热。

新增真实运输夹具位于 `X=1152…1632、Y=100、Z=64`，每组只清理相对 `X=-15…7、Y=-1…3、Z=-3…5` 的局部空间。`native`、`shared`、`topology`、`disconnect`、`unloaded` 五阶段分别建立自己的夹具，用注册机器与原生 GT 坩埚缓冲核对实际 HU 入账、损耗和余量；不手动修改网络的每 tick 去重标记。未加载边界用例只加载 `(8207,100,8200)` 所属区块，要求东侧相邻区块确实未加载，并断言测试后仍未加载。三张新配方（包含旧板转换）也通过实际 RecipeManager 查验。

结构检查同时读取游戏实际分派的选中与碰撞形状，验证低底架随成型、拆除、修复切换，而供热台保持完整方块。`fuels` 阶段通过真实物品能力和独立的原版材料热值基准验证原版及存在的 GT 煤/木炭/焦炭粉，检查正确灰种、整 U 数量和碎粉拒收。

`energy_gate` 阶段还用 GT 原生能量节点和仅供测试的可抽取 HU/KU 规格，检查宿主主动轮询不会绕过 HU 拒收规则，同时 KU 辅助通道仍正常扣款与入账。检查前先确认测试节点确实能模拟抽取，避免用只能主动输出的设备得出无效的拒收结论。

可用 `python scripts/testing/fluidized_bed_server.py --stage energy` 等有限阶段参数定位失败；单独阶段要求先执行 `prepare` 并完成其必要前序。运输专项可用 `python scripts/testing/heat_transport_server.py --stage shared` 单独重建并执行相应阶段；`unloaded` 要求边界邻块尚未加载。测试夹具的 NBT 往返检查不等同于完整服务器重启测试，服务端断言也不替代客户端的光照、动画和实际搭建观感验收。
